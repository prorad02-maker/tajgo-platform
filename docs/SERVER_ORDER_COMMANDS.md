# Серверные команды заказов TajGo

## Реализованный процесс

Callable `orderCommand`, регион `europe-west1`, Node.js 22. UID берётся из
Firebase Auth. Роли и одобрение курьера проверяются по серверным документам.
Новый заказ содержит `commandVersion: server-v1`. Критические записи клиента
для таких заказов запрещены Rules; при сбое функции обходного client-write нет.

Поддержаны создание доставки, checkout, предложение/отзыв/отклонение,
выбор/принятие, прибытие, забор, доставка, завершение с кодом, подтверждение,
спор, отмена и административные действия. Сервер проверяет актуальные товары,
цены, количество, координаты, свежесть GPS, занятость и переходы статусов.
Цены товаров считаются в сотых TJS; половина килограмма округляется один раз
на уровне строки корзины. Предложение курьера действует 5 минут.

Код генерируется на сервере, хранится как salted hash в `_order_secrets` и
проверяется сервером. Клиент получает код через собственный `order_receipts`.
Курьер и чужие пользователи не могут читать receipt. Код истекает через 24 часа;
после пяти разных неверных попыток требуется администратор. Повтор запроса
с тем же requestId не увеличивает счётчик ещё раз. Возврат на поиск меняет код.

Транзакции не допускают двух назначений или двух новых активных заказов
одного клиента. Старые активные заказы учитываются при создании нового.
Закрытие уже оплаченного спора не начисляет доход повторно и не очищает
более новый заказ курьера.

`_order_commands` хранит результат команды и fingerprint тела. Flutter
сохраняет requestId до вызова, повторяет его после timeout/restart и удаляет
после успешного результата или явного отказа. Журнал пока не имеет TTL:
его нельзя удалять произвольно, пока требуется гарантия повторов.

## Проверка без рабочего Firebase

Установить Node.js 22, Firebase CLI и Java 21+, затем:

```powershell
npm --prefix functions ci
$env:TAJGO_FUNCTIONS_EMULATOR_URL='http://127.0.0.1:5003/demo-tajgo-readiness/europe-west1/orderCommand'
firebase emulators:exec --only auth,functions,firestore --project demo-tajgo-readiness "npm --prefix functions test"
flutter analyze
flutter test
```

Используется `demo-tajgo-readiness`, включая Auth Emulator. Без Firestore
Emulator тестовый модуль прекращает работу. HTTP-тест проверяет настоящий
callable-протокол, токен Firebase Auth, отказ анонимному запросу и retry.
Firestore Emulator не подтверждает готовность production composite indexes.

## Последовательность публикации

1. Проверить diff, сохранённую копию опубликованных Rules и результат тестов.
   Публикация меняет доступ к рабочим данным и выполняется после подтверждения
   владельца. Подтверждение получено и шаги 2–4 выполнены 10 октября 2026.
2. Создать недостающие индексы и дождаться состояния READY:
   `firebase deploy --only firestore:indexes --project tajgo-4fcd0`.
3. Опубликовать отдельно новый codebase и Rules:
   `firebase deploy --only functions:order-commands,firestore:rules --project tajgo-4fcd0`.
   Отдельный codebase `order-commands` сохраняет три существующие функции.
4. Оставить `_config/order_commands.enabled` отсутствующим/false. Старые
   клиентские заказы продолжают обслуживаться. Новые Rules сохраняют процесс
   waiting и waitingOffers; завершение старой доставки проверено в Emulator.
5. Собрать тестовый клиент с `--dart-define=TAJGO_SERVER_COMMANDS_ENABLED=true`
   и пройти сценарий двух телефонов на выделенных тестовых аккаунтах.
   Проверить SMS, отмену GPS-permissions, возврат из background, потерю сети,
   получение кода, цену каталога, переключение ролей и административный спор.
6. После обновления пользователей отдельным контролируемым действием
   установить `_config/order_commands.enabled=true` через Admin SDK/Console.
   Это закрывает создание новых legacy-заказов. Старые сборки должны быть
   обновлены до этого шага; существующие legacy-заказы остаются обслуживаемыми.
7. Выпустить клиент с оригинальным production keystore и проверенными SHA.

## Откат

До первого server-v1 заказа возможен возврат к сохранённым Rules после проверки
совместимости. После появления server-v1 нельзя возвращать июльские Rules:
они не знают receipts и серверные ограничения. Отключить создание новых
серверных заказов в следующей сборке и оставить gate false, но сохранить новую
функцию/Rules для уже созданных server-v1 заказов. Пользовательские документы
и журнал не удалять. Заказ после timeout сначала найти через историю/active stream.

## Практические ограничения

- Радиус считается по координатам телеметрии курьера. Сервер проверяет время
  и accuracy, но без аттестации это не доказательство отсутствия GPS-spoofing.
- Сохранённая сервером дистанция/ETA пока является оценкой по координатам
  (`routeQuality: estimate`). Карты отдельно получают реальную геометрию дорог.
- Публичный OSRM не даёт production SLA; собственный endpoint/договор пока
  не найден. App Check enforcement выключен до регистрации реальных клиентов.
- FCM, Crashlytics/наблюдение и восстановление после длительного background
  требуют отдельной приёмки. Фото документов проверяются при личной встрече.
- Нужны реальный канал поддержки и утверждённая политика владельца
  (`TAJGO_SUPPORT_URL`, `TAJGO_PRIVACY_POLICY_URL`). Встроенная справка о данных
  не заменяет официальный документ для магазина приложений.
